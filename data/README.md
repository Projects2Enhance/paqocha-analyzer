# Data pipeline

One-time, offline generation of the static JSON the frontend fetches
directly — no database, no server-side lookup, no script runs as part of
`npm run dev`/`build`/`start`. Re-run by hand only when the raw inputs
change (a new corpus export, an updated inverted index).

Plain Node.js, no dependencies beyond what's already installed system-wide
— nothing added to `web/package.json`.

## Inputs (`raw/`, not generated, not modified by these scripts)

- `ss-corpus-qxp.tsv` — one row per recorded audio. Most rows have no
  `transcription` (6083 of 7305 data rows in the current export).
- `inverted_index.json` — per unique surface word: its morphosyntactic
  analysis (`morphology`) and every audio/position it occurs in
  (`postings`). ~33MB; not meant to be shipped to the browser as-is.
- `timestamps/<audio_file-without-.mp3>/alignment.json` — real
  forced-alignment word timestamps, one folder per transcribed audio
  (1222, matching `inverted_index.json`'s `index_info.indexed_audios_count`
  and the TSV's transcribed-row count exactly). `metadata.json` in the same
  folder duplicates that audio's TSV row and isn't read by these scripts.

## Run order

```
node scripts/build-audios.js
node scripts/build-clips.js
node scripts/build-search-index.js
node scripts/build-metadata.js
```

1. **build-audios.js** — TSV -> `processed/audios.json`: typed JSON array,
   keeping only rows with a non-empty `transcription`. Intermediate
   artifact for the next two scripts; not fetched by the app.
2. **build-clips.js** — for each audio in `audios.json`, reads its real
   `alignment.json`, looks up each transcript word (normalized the same
   way the frontend normalizes a search term — see
   `scripts/lib/normalize-word.js`) in `inverted_index.json` to assemble a
   word-by-word root/suffix breakdown, and writes one self-contained file
   per clip: `web/public/data/clips/<audio_id>.json` (`{ metadata,
   alignment, wordAnalysis }`). A transcript word not found in the index
   (proper noun, loanword, etc.) becomes its own unanalyzed root entry
   rather than being dropped, so the array's length/order always matches
   `alignment.word_segments` — required by how `KaraokePlayer` indexes
   into it.
3. **build-search-index.js** — strips `inverted_index.json` down to
   `{ "<normalized word>": [audio_id, ...] }`, dropping morphology/postings/
   context (already inside each clip file) -> `web/public/data/search-
   index.json`. Small enough to fetch whole on the client and look up with
   a plain object key — the expensive raw file never reaches the browser.
4. **build-metadata.js** — `audios.json` reshaped into one lean catalog,
   `{ "<audio_id>": AudioMetadata }` -> `web/public/data/metadata.json`
   (740KB for 1222 records). Fetched once so the frontend can render every
   match card a search returns (region, speaker, transcript excerpt,
   duration) without fetching each match's full `clips/<id>.json` — that
   file also carries real alignment timestamps and a full per-word
   morphosyntactic breakdown, needed only for whichever one match is
   actually selected/playing, not for every card in the list.

## What's committed

Only `scripts/` and this file. `raw/` (source TSV, inverted index, forced-
alignment timestamps) and `processed/` (intermediate `audios.json`) are
gitignored at the repo root — large, one-time inputs the scripts already
fully consumed into `web/public/data/`. `web/public/data/{metadata,
search-index}.json` and `web/public/data/clips/*.json` **are** committed
(the app fetches them at runtime and nothing else generates them in
production); `web/public/data/audios/` is gitignored — see "Audio hosting"
above.

## Output consumed by the app

```
web/public/data/
  search-index.json      fetch once, look up normalizeWord(query) -> audio_id[]
  metadata.json           fetch once, look up audio_id -> AudioMetadata (renders every match card)
  clips/<audio_id>.json   fetch only for the active match -> { metadata, alignment, wordAnalysis }
```

Shapes match `web/components/player/types.ts`'s `AudioMetadata`/
`Alignment`/`WordAnalysisData`/`ClipData`/`SearchIndex`. `KaraokePlayer`
fetches `search-index.json` + `metadata.json` once, resolves a query's
matches entirely from those two (no per-match fetch), and only fetches
`clips/<id>.json` for whichever one match is currently active — see
web/DESIGN.md -> Components -> KaraokePlayer.

## Audio hosting (CDN)

Audio files are **not** generated by these scripts and are **not** served
from `web/public/`. They live in the `paqocha-audio` Cloudflare R2 bucket
(managed outside this repo) and are served publicly through
`https://cdn-paqocha.iampol.dev/audios/<audio_file>` — the frontend's
`AUDIOS_BASE_PATH` (`web/components/player/karaoke-player.tsx`) points
there directly; a plain `<audio src>` needs no CORS headers, so this is a
same-origin-free static reference, not a fetch.

The bucket already holds the full corpus (every `audio_file` the pipeline
can reference); nothing needs to be re-uploaded for a normal pipeline rerun.
If a *new* audio is ever added to the corpus, upload it with the AWS CLI
(credentials/endpoint held outside this repo — ask whoever manages the R2
bucket):

```
aws s3 cp <file>.mp3 s3://paqocha-audio/audios/ --endpoint-url $EP --profile paqocha
```

The bucket caches each object for a year and must never receive a
same-name overwrite (its own rule) — a corrected re-recording needs a new
`audio_file` name, not a reused one.

`web/public/data/audios/` (if present locally) is a leftover local mirror,
gitignored and unused by the app — safe to delete.

## Known data-quality notes

- `wordAnalysis` morpheme `gloss`/`meaning` reuse `inverted_index.json`'s
  own Spanish linguistic fields (`name`/`role` for suffixes, `pos`/first
  sense definition for the root) as-is — there's no English gloss in the
  real data, unlike the earlier hand-authored example fixture.
- A transcript word with no entry in the index gets `gloss`/`meaning`
  `"—"` and no suffix breakdown.
